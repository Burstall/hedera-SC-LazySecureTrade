## 1. Post-deploy wiring

Order of operations after fresh contract deploys. Each step depends on
the previous one.

| # | Action | Caller | Notes |
|---|---|---|---|
| 1 | Deploy `LazySecureTrade` | operator | Constructor params: LAZY token, LGS, LDR, LSH_GEN1/GEN2/MUTANT addresses, listing cost, burn % |
| 2 | Deploy `BidderContract` (implementation) | operator | Constructor takes no args; locks `initialized=true` so the impl can't be hijacked |
| 3 | Deploy `BidderContractFactory(LST, LAZY, LGS, LDR, impl)` | operator | Wired against the LST from step 1 |
| 4 | `LST.authorizeFactory(BCF, true)` | LST owner | Grants BCF the right to call `createTradeOnBehalf` |
| 5 | `LST.setBcf(BCF)` | LST owner | **Phase 5 critical step.** First-time wire-up is **instant** (no timelock) because no stashes depend on the resolver yet. Subsequent rotations are 48h timelocked. Emits `BcfRegistered(0, BCF)` |
| 6 | `LazyGasStation.addContractUser(BCF)` | LGS admin | Lets stash clones refill HBAR allowance to LST via LGS |

**Failure to perform step 5** silently regresses stash-listed trades to
"Bug 3" behavior — the stash is charged the base fee rate (1%) instead
of the human owner's LSH tier. Check at deploy time: read `LST.bcf()`
via mirror; it must equal the BCF address.

`scripts/deployments/deployBidderContractFactory.js` prints a post-deploy
checklist as a `console.log` reminder. **Not enforced** — operators must
follow through.

## 2. BCF rotation (BCF v2 migration)

The LST `bcf` pointer is owner-settable to enable BCF v2 migration
without redeploying LST. The first-time wire-up is instant, but **any
subsequent change is 48h timelocked** so a briefly-compromised owner key
can't silently re-point beneficial-owner resolution to a malicious BCF.

### Migration strategy — pick one before T-0

The rotation has two viable strategies. Pick before T-0; they have
different tooling needs and different user-visible behavior.

**Strategy A — clean cut.** Old stashes are deprecated. Users
re-deploy on v2 via `deployStash()`. Old stashes still hold funds and
can be drained via `withdrawHbar` / `rescueHbar` / `withdrawNFTs`;
they just lose factory-mediated paths (bid/trade/arbitrage).
- **Pros:** zero on-chain mutation on v2 — no `seedStashOwners`
  function needed. Cleanest mental model. Stash addresses are
  function of (factory, impl, user) — a v2 factory at a different
  address predicts different stash addresses, so any "carry-over"
  in v2 storage would be at a *foreign* address that v2 didn't
  deploy. Strategy A avoids that inconsistency.
- **Cons:** users with funds + NFTs in old stashes have a manual
  migration UX. Lotto attribution (§3) handles the resolve in
  both directions — old or new BCF — as long as the scanner is
  configured with both addresses for the rotation window.

**Strategy B — absorb old stashes.** v2 BCF gains a
`seedStashOwners(address[] stashes, address[] owners) external onlyOwner`
function. Operator pre-seeds the new BCF's `stashOwnerOf` mapping
with the snapshot from the old BCF before flipping `LST.setBcf`. Old
stash addresses keep working under v2 — they were already deployed
clones with no factory-pointer, so the only data they need from BCF
is beneficial-owner resolution (which the seeded mapping provides).
- **Pros:** transparent migration — users see no change. No
  manual UX.
- **Cons:** requires a v2 BCF contract change to add the seed
  function. `userToStash[user]` would also need to track the old
  stash to avoid `deployStash()` re-deploying a v2 native one. Adds
  ~150-200 bytes to BCF (currently 18.368 KiB / 6.2 KiB headroom).
  Seed must run while the LST `bcf` pointer is still old (so v2
  isn't yet active) but the owner mapping is already populated.

The runbook recommends **Strategy A** unless there's a strong
product reason to keep specific stash addresses live across the
rotation. Most v2 motivations (bug-fix, gas reduction, new feature)
are compatible with users opting in via fresh deploys.

### Migration sequence — Strategy A

| # | Action | Caller | Timing |
|---|---|---|---|
| 1 | Pause new stash creation on old BCF (off-chain coordination — no on-chain pause; operators advise frontends + agents) | n/a | T-0 |
| 2 | Deploy v2 BCF | operator | T-0 |
| 3 | Snapshot old BCF `stashOwnerOf` mappings for lotto-attribution continuity (`node scripts/ops/snapshotStashOwners.js`) — output drives scanner config in §3 | operator | T-0 |
| 4 | Update LazyTradeLotto scanner config to recognize BOTH the old and new BCF addresses during the cutover window. Resolves stash→human from whichever BCF holds the mapping | LazyTradeLotto ops | T-0 |
| 5 | `LST.setBcf(newBCF)` — queues pending change | LST owner | T-0 |
| 6 | Wait 48h, monitoring for `BcfChangeCancelled` events (legitimate-owner override) | n/a | T-0 to T+48h |
| 7 | `LST.executeBcfChange()` — applies the change (**permissionless** after ETA) | anyone | T+48h |
| 8 | `LST.authorizeFactory(newBCF, true)` | LST owner | After step 7. First grant ever is instant; subsequent grants are 48h-timelocked (see `authorizeFactory` in `contracts/LazySecureTrade.sol`). On a fresh LST, this is instant |
| 9 | `LST.authorizeFactory(oldBCF, false)` | LST owner | After stashes have stopped using old BCF (instant — revoke is unconditional) |
| 10 | Announce migration UX: users with assets in old stashes call `withdrawHbar`/`withdrawLazy`/`withdrawNFTs` to drain, then `deployStash()` on v2 for a fresh stash | frontend / docs | T+48h onward |

### Migration sequence — Strategy B (additional steps)

Strategy B replaces step 3 with a snapshot + replay flow, runs
`seedStashOwners` on v2 before step 5, and keeps the legacy lotto
config (single-BCF) since the v2's `stashOwnerOf` already mirrors
old-BCF state.

| # | Action | Caller | Timing |
|---|---|---|---|
| 3a | `node scripts/ops/snapshotStashOwners.js --out=./snapshot.json` | operator | T-0 |
| 3b | `node scripts/ops/replayStashOwners.js --in=./snapshot.json` (dry-run; review output) | operator | T-0 |
| 3c | `node scripts/ops/replayStashOwners.js --in=./snapshot.json --execute --bcf-v2=<v2 id>` — submits the seed in batches of 50. **Requires v2 BCF to expose `seedStashOwners(stash[], owner[])`** — see design sketch below | operator | T-0, before step 5 |

#### Replay phase — `seedStashOwners` design sketch

If Strategy B is chosen, the v2 BCF must add this function (and ship
the ABI to the operator before snapshot replay):

```solidity
/// @notice One-time bulk seed of `stashOwnerOf` from a prior BCF
///         snapshot. Owner-only. Reverts after the first non-empty
///         deployStash() call to prevent post-launch mutation.
///         Pairs with `scripts/ops/replayStashOwners.js`.
function seedStashOwners(
    address[] calldata stashes,
    address[] calldata owners
) external onlyOwner {
    if (stashes.length != owners.length) revert ArrayLengthMismatch();
    if (allStashes.length > 0) revert SeedAfterLaunchBlocked();
    for (uint256 i; i < stashes.length; ) {
        address stash = stashes[i];
        address owner = owners[i];
        if (stash == address(0) || owner == address(0)) revert InvalidAddress();
        stashOwnerOf[stash] = owner;
        isValidStash[stash] = true;
        userToStash[owner] = stash;
        allStashes.push(stash);
        unchecked { ++i; }
    }
    emit StashOwnersSeeded(stashes.length);
}
```

Bytecode cost ~200 B. Add only when migration is imminent — don't
ship v2 with a no-op seed function and never use it.

### Window risks

- **Between step 7 and full snapshot replay** (Strategy B only):
  stashes deployed under the old BCF whose owner data was missed by
  the replay silently regress to base-fee behavior. Mitigate by
  re-running snapshot until `entries.length == getStashCount()` on
  the source BCF, then replaying.
- **Between step 5 and step 7:** the live `bcf` pointer is still
  the old BCF. Resolution works normally. **No regression in this
  window.**
- **Strategy A only — lotto cutover dual-config window:** between
  steps 4 and 9, the scanner must resolve against either BCF. If a
  trade involves a v2-native stash but the scanner's dual config
  has been removed, the lotto envelope is mis-attributed. Mitigate
  by keeping the dual config live until §3's "Verification" rows
  are signed off.

### Aborting a migration

If the queued change at step 5 is wrong (operator error or compromise):
- LST owner calls `LST.cancelBcfChange()` — clears `pendingBcf` and
  `pendingBcfEta` to zero. Emits `BcfChangeCancelled`.
- Re-queue a correct change if needed; the next `setBcf` call overwrites
  the pending value (does not stack).
- If Strategy B was in flight and `seedStashOwners` already ran on
  v2, the seeded state is harmless until `LST.setBcf` flips. v2 is
  inert in the system without that pointer.

## 3. LazyTradeLotto scanner cutover coordination

> **Status:** doc-ready, scanner change pending. Tracks against
> `D:\github\hedera-SC-lazy-lotto`. Block BCF mainnet activation until
> this checklist's "Verification" rows are signed off.
>
> **Handoff prompt:** `docs/LOTTO-SCANNER-CUTOVER-PROMPT.md` is a
> self-contained brief to drop into the `hedera-SC-lazy-lotto` repo as
> `CLAUDE.md` — a cold Claude session can make the scanner change from
> it without reading this repo first. This section is the ops-side
> coordination view; that file is the implementer-side prompt. Keep
> the two in sync if the event shape or BCF surface changes.

LazyTradeLotto credits users for trades they participated in. The
contract trusts an off-chain signer that watches LST `TradeCompleted`
events and signs eligibility envelopes for the `rollLotto(...)` call.

### Phase 1 attribution change

Phase 1 of v0.3 introduced beneficial-owner resolution. For lotto
attribution, this means:

- If a trade involves a stash (as seller or buyer), the **human owner**
  should be credited, not the stash address.
- Before Phase 1: stash addresses were the on-chain identity; lotto
  credits would route to stash (no spending path).
- After Phase 1: the scanner must resolve stash → human via
  `BCF.stashOwnerOf(addr)` before signing.

### Scanner code change — pseudocode

The scanner pulls `TradeCompleted` event params from the mirror feed
and signs an envelope keyed on `(recipient, tradeId, ...)`. Insert the
resolve hop between event parse and signature:

```javascript
// ACTUAL event shape (LazySecureTrade.sol:84):
//   event TradeCompleted(
//       address indexed seller,
//       address indexed buyer,
//       address indexed token,
//       uint256 serial,
//       uint256 nonce
//   );
// NOTE: there is NO tradeId / hbarPaid / lazyPaid field. The trade
// identity is keccak256(abi.encodePacked(token, serial)) computed
// off the event (matches LST's internal trade key). `nonce` is the
// per-(token,serial) sequence number — include it in the envelope
// key if your lotto contract needs replay-distinct identities.

async function attributeTrade(event, bcf, signerKey) {
    const tradeKey = ethers.solidityPackedKeccak256(
        ['address', 'uint256'], [event.token, event.serial],
    );
    const sellerResolved = await resolveStashOwner(bcf, event.seller);
    const buyerResolved  = await resolveStashOwner(bcf, event.buyer);

    // Sign one envelope per side — the lotto contract scores both
    // participants. Both sides are always set on a TradeCompleted.
    return [
        signEnvelope({ recipient: sellerResolved, tradeKey, nonce: event.nonce, side: 'sell' }, signerKey),
        signEnvelope({ recipient: buyerResolved,  tradeKey, nonce: event.nonce, side: 'buy'  }, signerKey),
    ];
}

async function resolveStashOwner(bcf, addr) {
    // `stashOwnerOf` is a public mapping on BCF (BidderContractFactory.sol:66)
    // → returns the human owner for a registered stash, or address(0)
    // for any non-stash address. A single read answers both "is this a
    // stash?" and "who owns it?", so no separate isValidStash pre-check
    // is needed (both are equal-cost SLOAD-via-eth_call).
    const owner = await bcf.stashOwnerOf(addr);
    // Fallback: address(0) means `addr` isn't a registered stash (a
    // normal EOA trade) OR a v2-migration replay gap. Either way,
    // attribute to the raw address — better an EOA credit / orphan
    // envelope than a silent miss.
    return owner === ethers.ZeroAddress ? addr : owner;
}
```

LazyTradeLotto ops owner. The lotto repo (`hedera-SC-lazy-lotto`)
should track these as issues / PRs.

- [ ] Scanner code change merged in `hedera-SC-lazy-lotto`

- [ ] **Worked test:** trigger a stash-side trade on testnet
      (e.g. via `scripts/interactions/createTrade.js` against

### Failure mode if cutover lags BCF mainnet

Stash trades produce lotto envelopes addressed to stash addresses.
Stashes don't have an EOA call path to `rollLotto` (it's `external
nonReentrant` — the stash could forward but no UX exists for it).
Effect: **lotto credits are stranded** until the scanner catches up
and re-issues envelopes.

**Cleaner mitigation:** block stash-creation on BCF mainnet until
scanner is live (off-chain coordination — there is no on-chain pause
on `deployStash`). Cheaper than fixing stranded envelopes
retroactively.

## 4. Emergency response

### Factory compromise

If the BCF is compromised (owner key leak, or unexpected behavior):

1. `LST.authorizeFactory(BCF, false)` — revokes the BCF's
   `createTradeOnBehalf` access. Existing trades listed via the BCF
   remain executable, but no new stash-listed trades can be created.
2. `LST.setBcf(newBcfOr0)` — queues a 48h-timelocked switch to a new
   BCF or to `address(0)` (opt-out). During the 48h window, resolution
   still uses the live (compromised) BCF — accept this risk OR
   pre-deploy a new BCF and queue the swap *before* the compromise.
3. Communicate to stash owners: they can call `detachFromFactory()` to
   permanently sever their stash from the BCF and then use
   `rescueHbar` / `rescueLazy` / `rescueNFT` to extract funds.

### Stash implementation bug

The stash implementation is immutable (`BIDDER_CONTRACT_IMPLEMENTATION`
in BCF is set once at deploy). If a bug is found post-deploy:

1. No retroactive fix is possible for deployed clones — they share the
   buggy impl bytecode.
2. Mitigation: deploy a v2 implementation, deploy a v2 factory that
   uses it. Existing stashes do NOT auto-migrate; their addresses are
   derived from the v1 factory + impl. Users must:
   - `detachFromFactory()` (severs the buggy stash)
   - Extract funds via `rescueHbar` / `rescueLazy` / `rescueNFT`
   - Deploy a new stash under the v2 factory
   - Re-deposit funds
3. The new factory's stash addresses will NOT match the old factory's
   — predicted addresses change. Off-chain code that hardcodes stash
   addresses must update.

### Owner key compromise

The LST and BCF owner keys control:
- `LST.authorizeFactory` (which factories can list trades)
- `LST.setBcf` (which factory is used for beneficial-owner resolution
  — **48h timelocked**)
- `LST.cancelBcfChange` (legitimate-owner override during the timelock
  window)
- `LST.setLazyCostForTrade`, `LST.updateFeeRates`, etc.
- `BCF.setArbitragePayoutBps` (48h timelocked)
- `BCF.withdrawProtocolProfit`

Recovery if a brief compromise occurred:
- If a `BcfChangePending` event fires that the legitimate owner didn't
  authorize, the legitimate owner has 48 hours to call
  `cancelBcfChange()` (or to escalate via the multisig).
- Other instant-effect owner functions (authorizeFactory, fee rates,
  protocol profit withdraw) cannot be reversed — they execute
  immediately. Future hardening (post-mainnet): consider applying the
  same 48h timelock pattern to other high-blast-radius owner functions.

## 5. Event schema notes for indexers

### `agentKey` / `agentReasoningTopicId` (reserved fields)

Present on `BidCreated`, `BidCancelled`, `BidExecuted`, `BidExpired`,
`ArbitrageExecuted`. **Always `bytes32(0)` in v0.3.** Reserved for the
upcoming agent marketplace flow. Indexers should:
- Skip filtering on these fields during v0.3
- Treat any non-zero value (post-agent-envelope) as agent-originated

### `bid.lazyAmount` field

Present on `BidExecuted` and `ArbitrageExecuted`. **Always `0` in v0.3**
because BCF bids are HBAR-only on this branch. Reserved for future
LAZY-priced bids. Indexers can safely use this as the LAZY-side
component when LAZY bids ship; in v0.3, treat as "no LAZY component."

### Bid lifecycle is event-driven (hard-delete)

Closed bids (Cancelled / Executed / Expired) are **hard-deleted** from
`bidRegistry`. Storage reads against a closed bid return a zeroed
struct. Indexers must consume the bid lifecycle events (especially
`BidCancelled` / `BidExecuted` / `BidExpired` / `ArbitrageExecuted`) as
the canonical history layer — storage will not give you historical bid
data.

### Cold-start indexer reconstruction

`BidExecuted` and `ArbitrageExecuted` carry the bid's `user`, `token`,
`hbarAmount`, `lazyAmount` so an indexer joining mid-stream can
identify the affected bidder, collection, and price without backfilling
the original `BidCreated`. `BidCancelled` and `BidExpired` carry
`token` for the same reason.

### Beneficial-owner attribution

`trade.seller` may be a stash address. To attribute trade activity to
the human owner, resolve via `BCF.stashOwnerOf(seller)` — if the
result is non-zero, that's the human; if zero, the input address IS the
human owner (an EOA, not a stash).

## 6. Monitoring + alerts

Recommended monitors for a v0.3 production deployment:

| Signal | Threshold | Action |
|---|---|---|
| `BcfChangePending(_, _)` event on LST | Any | Verify the queued BCF matches the operator's planned migration. If unexpected → page on-call; legitimate owner calls `cancelBcfChange()` within 48h |
| `BcfRegistered(_, 0x0)` event on LST | Any | LST has been opted out of beneficial-owner resolution. Verify intentional. Otherwise, every stash-listed trade silently regresses to Bug-3 behavior |
| `FactoryAuthorized(_, true)` for an unrecognized factory | Any | Verify the factory matches a known/expected deployment. Otherwise possible owner key compromise |
| `LST.bcf()` mirror read == `address(0)` post-deploy | Single sample | Operator forgot step 5 of post-deploy wiring. Halt new stash creation until fixed |
| `tokenToBids[token].length` per active collection | > 180 | Approaching the `MAX_VIEW_PAGINATION = 200` cap. Run `cleanupExpiredBids` to prune dead entries before `getBestBidForToken` truncation produces wrong best-bid answers |
| `pendingProtocolProfit` on BCF | Steady-state growth rate | Confirms arbitrage flow is generating fees. Sudden drop may indicate a fee-tier resolution regression |

## 8. EnglishAuction operational notes

EnglishAuction is a standalone listing surface — it does NOT route
through LST or BCF. The contract holds bidder escrow in HBAR or LAZY
and bundled NFTs+FTs from the seller, then atomically distributes at
settle. Cancellation is only allowed before the first bid.

### Post-deploy wiring (one-time)

| # | Action | Caller | Notes |
|---|---|---|---|
| 1 | Deploy `EnglishAuction` | operator | Constructor: LAZY, LGS, LDR, LSH_GEN1/MUTANT/GEN2, LazyNFTStaking (or address(0)) |
| 2 | `LazyGasStation.addContractUser(EnglishAuction)` | LGS admin | Lets the auction contract draw LAZY for FT-denominated bundles |
| 3 | Fund EnglishAuction with HBAR (~10 HBAR) | operator | Each NFT escrow leg pays a 1-tinybar custody hop. 10 HBAR ≈ 10⁹ legs |
| 4 | `EnglishAuction.setBcf(BCF)` | auction owner | **Instant** on first call (no timelock). Required for stash → human beneficial-owner resolution in the self-bid gate |
| 5 | `EnglishAuction.setVipSubscription(VIP)` | auction owner | Optional. Wires paid-tier discounts at settle |
| 6 | Tune defaults: `setDurationLimits` / `setDefaults` / `setProtocolFeeBps` / `setSettlementBountyBps` | auction owner | Optional; constructor sets sensible defaults |

Subsequent BCF rotations are 48h timelocked via `pendingBcf` /
`executeBcfChange` / `cancelBcfChange` (mirrors LST). Protocol fee
and settle bounty are instant (capped at 10% and 5% respectively).

### Bytecode + subcall budget

- Deployed size: 23.725 KiB / 24.0 KiB (~275 B headroom)
- Worst-case settle subcall budget (10-item bundle, 3 unique NFT
  collections with royalties, LAZY payment): ~16-20 subcalls
- Single cryptoTransfer batches escrow / release of bundles up to
  the per-call HTS limit (~10 token transfer entries per call)

### Bundle constraints (Tier C)

- `MAX_BUNDLE_ITEMS = 10` total, any mix of NFTs and FTs across
  arbitrary tokens
- Same-collection multi-serial bundles work via individual items
- Royalty is snapshotted per unique NFT collection at create via
  HTS `getTokenInfo`, paid manually at settle in the payment
  currency. FTs do not contribute royalty.
- Token association: contract auto-associates each new token on
  first encounter. ~1M gas per association (one-time per token).

### Settlement failure modes

EnglishAuction uses push-with-fallback pull-payment for value
distributions. If a recipient's `receive()` reverts:
- Bidder refunds (outbid): always queued (`claimableHbar` /
  `claimableLazy`). Pulled via `claim(PaymentToken)`.
- Seller proceeds at settle: push attempted, fallback to claim queue.
- Royalty collector: push attempted, fallback to claim queue.
- Settler bounty: always queued.
- Bundle delivery to winner: **no fallback** (size budget). If the
  winner is unassociated with one of the bundle's tokens at settle
  time, the entire settle tx reverts. Winner must associate and
  retry `settle()`. The auction state stays Open until settle
  succeeds — no partial state. Counts on EVM atomicity. Settle is
  permissionless after `closeAt`, so anyone can re-invoke.

### Pause response

If a bug requires emergency response:
- `EnglishAuction.setPaused(true)` — blocks new `createAuction` +
  `placeBid` + `buyNow`. Existing auctions continue to settle and
  refunds remain claimable, so escrowed funds + NFTs can always exit.
- Resume via `setPaused(false)`.

### Monitoring

| Signal | Threshold | Action |
|---|---|---|
| `BcfChangePending` on EnglishAuction | Any | Verify the queued BCF matches the planned migration. Cancel within 48h if unexpected |
| `AuctionSettled(success=false)` rate | > 30% over 24h | Investigate — may indicate reserve prices set too high or bot-bidder dropout |
| `AuctionExtended` events | Sudden spike on one auction | Possible bid-griefing attempt. The 24h `maxCloseAt` cap auto-limits damage |
| `claim` event rate vs `BidCreated` outbid rate | < 50% of outbids claim within 7d | Stale refund queue accumulating. Frontend prompt opportunity |
| `protocolFeeBps == 0` and seller is Free tier | Unexpected | LSHTierLib resolution regression — page on-call |

### Open product calls

- **Frontend auto-settle pattern.** With `settlementBountyBps = 10`
  (0.1%), bots have a thin economic incentive to settle. Until a
  Hedera keeper-bot ecosystem develops, the frontend should
  auto-settle on the winner's or seller's next page visit. Revisit
  bounty when settle latency becomes a UX issue.
- **Pull-payment refund discoverability.** Outbid bidders may not
  know they have HBAR queued. Frontend should auto-claim on every
  page load if `claimableHbar[user] > 0`.
- **Anti-snipe legibility.** Display two timestamps: "Soft close:
  T" and "Will close after N minutes of no bids." Render the
  extension policy BEFORE bids fire it.

### Test infrastructure note

Tests against Hedera testnet cannot manipulate `block.timestamp`.
The test suite splits timing-bound tests behind
`RUN_TIMING_TESTS=1` so the default CI sweep stays under ~5 minutes.
Set the env flag to exercise the full auction lifecycle (create →
bid → wait → settle → claim).

## 9. Agent envelopes (v0.3 stash agent subsystem)

Added in the v0.3 agent envelope work — per-user stashes authorize
agent keys to act within daily HBAR + LAZY budget caps. Envelope state
is owned by the stash (`BidderContract`); per-tier upper bounds live
on the factory (`BidderContractFactory.agentTierLimits`) and are
gated by a 48h timelock per tier after the initial wiring.

### Locked default tier table

Wired by `scripts/interactions/wireAgentTierLimits.js` after BCF
deploy. The first `setAgentTierLimits` call per tier is INSTANT so
an operator can wire all five rows in one session before users start
creating envelopes.

| Tier | Slots | Daily HBAR | Daily LAZY | Per-tx HBAR | Per-tx LAZY |
|------|-------|------------|------------|-------------|-------------|
| Free | 0 | — | — | — | — |
| Bronze | 1 | 500 | 5,000 | 200 | 2,000 |
| Silver | 2 | 1,500 | 15,000 | 500 | 5,000 |
| Gold | 3 | 3,500 | 35,000 | 1,000 | 10,000 |
| Platinum | 5 | 10,000 | 100,000 | 2,500 | 25,000 |

Free tier is zero-filled — `getAgentTierLimits(Free)` returns a
zero struct, which `BidderContract.createEnvelope` treats as "no
envelopes permitted." No explicit setter call needed for Free.

### Tier-table adjustment runbook (post-launch)

Every `setAgentTierLimits` call AFTER the first one for a given
tier enters a 48-hour timelock. Apply the queued change with
`executeAgentTierLimitsChange(tier)` (permissionless after ETA) or
abandon with `cancelAgentTierLimitsChange(tier)` (owner-only).

```
# T+0:  Propose a Bronze tier raise.
BCF.setAgentTierLimits(Bronze, {maxAgents: 2, ...})
# event: AgentTierLimitsChangePending(Bronze, ..., eta=T+48h)

# T+0 to T+48h:  Notice window. Frontend should surface the
# pending change to existing Bronze-tier envelope holders. If the
# change is hostile (compromised owner), legitimate owner can:
BCF.cancelAgentTierLimitsChange(Bronze)
# event: AgentTierLimitsChangeCancelled(Bronze)

# T+48h:  Apply the queued change (anyone can call).
BCF.executeAgentTierLimitsChange(Bronze)
# event: AgentTierLimitsSet(Bronze, {maxAgents: 2, ...})
```

**Important:** lowering a tier's caps via this flow does NOT
cancel existing envelopes that exceed the new caps. They run to
their own `expiresAt` on the cap they were created with. New
envelope creation against the new (lower) caps starts immediately
after execution. Communicate cap reductions ≥ 48h ahead so users
can plan around them.

### Agent kill-switch — emergency response

Available to the stash OWNER (no timelock — these are the panic
buttons):

```
# Kill ONE agent. Surgical.
BidderContract(stash).pauseAgent(agentKey, true)
# Reversible: pauseAgent(agentKey, false)

# Kill ALL agents. Nuclear — every envelope on this stash returns
# `EnvelopeAuthFailed(AllAgentsPaused)` for any signed action.
BidderContract(stash).pauseAllAgents(true)

# Permanent revoke. Hard-deletes envelope storage; agent must be
# re-registered to resume.
BidderContract(stash).cancelEnvelope(agentKey)

# Nuclear: empty the stash entirely. Pre-existing escape hatch.
BidderContract(stash).rescueHbar(to, amount)
BidderContract(stash).rescueLazy(to, amount)
```

Rotate the compromised agent key off-chain (the agent runtime
stops signing), then `cancelEnvelope` + `createEnvelope` with a
fresh agentKey.

### Monitoring + alerts

- **`EnvelopeBudgetConsumed`** (per agent action): track
  `remainingHbar` / `remainingLazy` per envelope; alert at 90%
  consumed for ops awareness.
- **`EnvelopeDailyReset`**: emitted on the first action of a new
  UTC day. Useful to confirm reset semantics are firing.
- **`EnvelopePaused`** / **`AllAgentsPaused`**: alert immediately —
  these usually fire during incident response and ops needs to
  know whether the user triggered them.
- **`EnvelopeCreated`** / **`EnvelopeCancelled`**: lifecycle
  attribution; indexers should subscribe to both for the agent
  registry view.
- **`AgentTierLimitsChangePending`** with a 48h ETA in the future:
  schedule a follow-up alert for the ETA to verify whether the
  change was executed or cancelled.

### Agent authentication model

Agents are normal Hedera accounts. Either key type works — ECDSA
secp256k1 OR ED25519 Hedera-native. The on-chain authentication is
`msg.sender == envelope.agentKey`. Hedera's protocol layer verifies
the agent's transaction signature (against whatever key type the
agent's account holds) before the EVM runs; by the time the contract
executes, `msg.sender` is guaranteed by consensus to be the verified
signer. The contract does NOT perform EIP-712 / ecrecover ceremony —
that would be redundant AND would exclude ED25519 agents.

Operational implications:

- **Agent runtime needs its own Hedera account.** The agent submits
  transactions; Hedera requires a payer. The stash CAN sponsor agent
  gas via HIP-906 HBAR allowance (`hbarApprove(stash, agentAccount,
  N)`), but the agent's account itself is unavoidable.
- **Authorize the agent's EVM address.** ECDSA accounts have an EVM
  alias address; ED25519 accounts have a "long-zero" address
  (`0x0000...XXXX` where the suffix encodes the account ID). Either
  format is accepted at `createEnvelope` — but the address must match
  whatever Hedera presents as `msg.sender` when that account calls.
- **Contract addresses are rejected.** `createEnvelope` reverts with
  `AgentKeyIsContract` if the supplied agentKey has non-zero bytecode
  at the time of registration. Required because a contract can be
  called by anyone, propagating msg.sender — auth would devolve to
  "whoever can call the contract" instead of "the agent operator".

`test/AgentEnvelope.test.js` covers the critical paths (envelope

### Known gaps (deferred follow-ups)

- **LST `authorizeFactory` 48h timelock** — security finding H3 from

- **EnglishAuction AgentAuth threading** — `createAuction` / `placeBid` /

- **Daily reset + multi-day budget tests** — gated behind

  rollover or a test-only override path. See QA agent's design plan

## 10. LDR health probe (off-chain degradation monitoring)

**Why this exists.** `LazyDelegateRegistry` (LDR) is immutable and
has known revert paths. Every LDR call in tier resolution is wrapped
in try/catch (`LSHTierLib._safeDelegatedLength`, LSHTierLib.sol:201-213)
so an LDR revert never bricks a trade — the user silently degrades to
their **holdings-only** tier (delegated tokens stop counting toward
the fee tier until LDR recovers).

This degradation is **benign and self-healing** — a transient fee-tier
downgrade for the duration of the LDR outage, not a fund-loss event.
But it is **silent**: there is no on-chain signal that it happened. An
on-chain `LDRDegraded` event was considered and **rejected as won't-fix**
(working plan item #6) — it would force the whole `view` tier-resolution
chain to drop `view` and push LST over the 24 KiB bytecode ceiling, to
capture a rare transient edge case. Off-chain monitoring covers the
need at zero contract cost; this section is that monitoring.

**What to monitor.** LDR's own behavior, directly, from ops infra:

1. **Periodic synthetic probe.** On a schedule (e.g., every 15 min),
   call `LazyDelegateRegistry.getSerialsDelegatedTo(<known delegatee>,
   <known LSH token>)` via a mirror-node `eth_call` for an address you
   know has an active delegation. Expected: a non-empty array. If the
   call **reverts** or returns empty for a known-good delegation, LDR
   is degraded → page ops. This is the same call the contract makes,
   so it fails (or succeeds) in lockstep with the on-chain path.

2. **Tier cross-check (optional, higher-fidelity).** Compare
   `LST.getLSHTokenTier(user)` (or `LSHTierLibProbe.tierFor`) against
   an independently computed "expected tier" for a small set of known
   delegatee accounts. A user who *should* be Platinum-via-delegation
   but reads Free is a live degradation signal. Run this against a
   curated watchlist, not all users (it's a read per user).

**Implementation note.** No dedicated script ships in-repo yet —
this is a documented ops requirement, not code. When wiring mainnet
monitoring (pre-mainnet checklist → "On-chain event monitoring"),
add the LDR probe as one more check alongside the timelock-pending
alerts. The probe is a plain mirror-node `eth_call`; reuse the
read pattern in `utils/hederaMirrorHelpers.js`
(`readOnlyEVMFromMirrorNode`).

**Alert semantics.** LDR degradation is **warning**, not critical —
trades still execute, users just pay holdings-only fee tiers
temporarily. Alert ops for awareness + so support can explain a
"why am I being charged base fee?" ticket, but do NOT trip emergency
response (§4) — there is nothing to pause or roll back. The condition
clears itself when LDR recovers.
