## State Build-Up — RESOLVED

The unbounded storage growth concern raised by the architect and performance agents has been fully addressed:

**Before (soft-delete)**: Closed bids retained their full `BidDetails` struct (including the dynamic `uint256[] serials` array) permanently in `bidRegistry`. At 10-12 storage slots per bid, 10,000 historical bids would accumulate ~38 MB of unreclaimable state.

**After (hard-delete, commit `24e1855`)**: `_closeBid()` now calls `delete bidRegistry[bidId]` after removing the bid from discovery arrays. All storage slots — including the dynamic serials array — are zeroed and reclaimable. The event stream (`BidCancelled`, `BidExecuted`, `BidExpired`) carries the terminal state for anyone who needs historical bid data. The Directus-backed event scanner + bid cache is the off-chain history layer.

**Net effect**: on-chain storage only holds *live* bids. Closed bids consume zero storage. The `tokenToBids` and `userToBids` arrays are cleaned via O(1) swap-pop on close. The only append-only structure remaining is `allStashes` (one entry per user, ever), which now has `getStashesPaginated` for bounded reads.

## Product Items — Open from Panel Review

The product agent identified three items. Here's their status:

### 1. Gas budget table per user action — NOT YET DONE

**Why it matters**: Frontend developers will guess gas limits during integration, causing trial-and-error and wasted testnet HBAR. A concrete reference eliminates this friction.

**Proposed table** (estimates, to be validated during your testnet run):

| Action | Est. gas | Notes |
|---|---|---|
| `deployStash` | ~1.5M | Includes LAZY token association (~950K) |
| `createBid` (existing token assoc) | ~500K | Token already associated to stash |
| `createBid` (new token assoc) | ~1.5M | +950K for first-time NFT collection |
| `cancelBid` | ~200K | O(1) swap-pop + storage delete |
| `executeAgainstBid` | ~1.5M | Factory → LST → 2-step NFT transfer |
| `executeArbitrage` | ~2M | Factory → LST → transfer + settle |
| `claimArbProfit` | ~150K | Simple HBAR send |
| `rescueHbar` / `rescueLazy` | ~100K | Raw call / transfer |
| `rescueNFT` | ~800K | moveNFTs + refill check |
| `detachFromFactory` | ~100K | Storage write + event |
| `cleanupExpiredBids(10)` | ~500K | 10 bids × O(1) delete each |

**Action**: validate these during testnet run, then add to `docs/v0.3-integration-guide.md`.

### 2. Best-bid / floor-price aggregation view — DONE

`getBestBidForToken(address token)` was added in commit `24e1855`. Returns `(bytes32 bestBidId, uint256 bestHbar)` — scans up to `MAX_VIEW_PAGINATION` (200) active bids and returns the highest HBAR bid. For collections with more than 200 active bids, the frontend should page via `getBidsForTokenPaginated` and compute best-bid client-side.

### 3. First-party arb bot / matching service — NOT YET DONE

**Why it matters**: The arbitrage mechanic is sound, but on Hedera (no MEV, no mempool bots) there's no organic arb infrastructure. Without a matching service, bids and asks sit unmatched until a human notices the spread.

**Recommendation**: Ship a reference matching bot as a simple cron script that:
1. Scans `getBidsForTokenPaginated` for active bids
2. For each bid, queries LST for open-market trades on the same token
3. If `trade.tinybarPrice < bid.hbarAmount` and `trade.tinybarPrice >= bid.minAcceptablePrice`, calls `executeArbitrage`
4. Runs on a 30-60s interval via cron or a long-running process

This could be a ~150-line Node.js script in `scripts/bots/arbMatcher.js`. It doesn't need to be sophisticated — just match obvious spread opportunities. The smart contract handles all the safety (self-arb block, price floor, BPS cap).

**Priority**: Medium. Not blocking testnet validation or mainnet deploy, but should exist before the marketplace is promoted to users. Without it, the bid system is "write-only" until someone builds the matching layer.

## Summary

The v0.3 architecture is **implementation-complete**. The second-pass panel confirmed that 20+ of the original ~25 critical findings are resolved in code, and the remaining items (7 tests, gas table, arb bot) are execution tasks that require your live testnet environment.

The state build-up concern is fully resolved — hard-delete means closed bids consume zero on-chain storage. Events are the history layer. The only remaining growth vectors are `allStashes` (one entry per user lifetime, paginated) and `tokenToBids`/`userToBids` (only live bids, cleaned on close).

The two product-level gaps are: (1) a gas budget reference table (validate during testnet, 15 min to document), and (2) a first-party arb matching bot (2-3 hours, can ship post-launch but should exist before promotion).

Everything else is green. Run the tests, validate the gas estimates, and you're mainnet-ready pending the multisig ceremony.
